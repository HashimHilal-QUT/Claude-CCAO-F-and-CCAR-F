Agentic Architecture & Orchestration

Cold open: the refund that never happened

Before we start, a story. The refund that never happened.

A customer writes in about a damaged parcel. The support agent looks up the order. It says it will check the refund policy. And then it goes quiet.

The case is logged as resolved. No refund was issued. No escalation ticket exists. And nobody notices for three weeks, until the customer complains in public.

When the engineers pull the transcript, nothing is broken in the ordinary sense. No error. No crash. The agent simply stopped. And the code around it took stopping to mean finished.

On another run, the same agent looked up the same order, with the same arguments, twenty-eight times in a row. It only ended when a counter finally cut it off.

What do those two failures have in common? The same root. Nobody outside the model was deciding when the work was actually done.

That is what this chapter is about.

This is Domain one, Agentic Architecture and Orchestration. It is twenty-seven percent of the exam. The heaviest domain. Roughly sixteen of the sixty questions.

It has seven task statements, and we take them in order. Loops. Coordinators and subagents. Spawning subagents and passing context. Enforcement and handoffs. Hooks. Decomposition. And sessions.

One thing to hold on to before we start.

Questions in this domain almost always show you a system that already works, and is now failing in some specific, measurable way. You are asked for the structural fix.

The wrong answers are usually real fixes. Just for a different problem.

And the exam rewards one move above all others. Hold on to this line. Take a rule out of the prompt, and put it into code.

Part one: Agentic loops

Part one. Agentic loops.

This is task statement one point one: design and implement agentic loops for autonomous task execution. By the end of this part, you'll know how to read why the model stopped, how to handle each reason, and why the decision to stop belongs to your code, not the model.

Start with the difference between asking and sending.

Ask a friend a question, and you get one answer. Then it's over.

Now send that friend to the shops with a list. Something different happens. They find an item out of stock, and pick a substitute. They see a long queue, and try another till. You scripted none of that. They made a series of small decisions on the way to the goal.

That's the difference between a single call to a model and an agent. The same ability to produce an answer, wrapped in a loop.

The model picks an action. Your code carries it out. The result goes back in. The loop runs again.

Here's the part architects get wrong.

A real friend gets tired and comes home. An agent doesn't. It has no clock. No fatigue. And no view of your bank balance.

It will keep taking reasonable-looking next steps until something outside it says stop.

So who decides when to stop? You do. The decision to stop belongs to you.

In plain terms, every time the model stops producing text, it tells you why.

It finished its thought. It hit a length limit. It's waiting for you to run something. It paused partway. Or it declined.

Your code reads that note, and does something different for each one.

But here's what the note never says. It never says the job is done. It only says the model stopped talking.

The technical name for that note is the stop_reason field. The Messages API, the application programming interface you call directly, documents seven values.

One. end_turn. Two. max_tokens. Three. stop_sequence. Four. tool_use. Five. pause_turn. Six. refusal. And seven. model_context_window_exceeded.

The documentation's advice is blunt. Always check stop_reason.

Let's take three of them now.

tool_use means the model has asked for one or more tools, and is waiting. Your loop runs every requested call, then continues.

end_turn means the model finished its turn on its own. That's your normal exit. But it is only a candidate for success. Never proof.

stop_sequence means the model emitted one of the stop strings you configured. A companion field tells you which one fired, so you branch on that.

The other four, we'll take one at a time.

Quick recap before the first question. The model always tells you why it stopped. It never tells you the job is done. You branch on the reason.

Question one. The waiter who walks away too early.

Here's the scenario. An invoice extraction agent runs a hand-written loop. The loop exits as soon as the first content block of a response is text. About one invoice in twelve ends with no record, and no error.

The transcripts show a final response with a short line of text. Something like "let me check the vendor master first". Followed by a tool request.

What's going on?

Take a second.

Think of a waiter who hears a diner say "hmm, let me think," and walks away. The words sounded like the end. But the diner hadn't closed the menu. They were about to order.

The answer. In exam terms, one response can carry a text block and a tool_use block together. The model often thinks out loud before calling a tool, and that's normal.

The stop_reason on that response is tool_use. The model is waiting for a result.

A loop that checks the type of the first content block exits in the middle of the task. And it silently drops the tool call.

The fix is to branch on stop_reason. Continue on tool_use. And handle every other value explicitly.

Now the wrong turns.

Wrong: max_tokens is too low, and the response was truncated. Why? Truncation shows up as a max_tokens stop reason with incomplete content. These transcripts contain a complete tool request.

Wrong: the vendor master tool returned an empty result. Why? That tool never ran. The loop exited first.

Wrong: a missing turn cap, and a scheduler killing long runs. Why? A scheduler kill leaves no clean final response. These runs have one.

The constraint that decides it is the phrase "a text block followed by a tool_use block." Content type and stop_reason measure different things.

Hold on to this line. Branch on why the model stopped, never on what it happened to say.

Question two. The pen pal who forgets everything.

Here's the scenario. To cut token spend, an engineer changes the loop. After each tool call, it sends back only the tool result. It skips the assistant message that held the tool request.

Requests start failing with errors on the second iteration.

Why?

Take a second.

Picture a pen pal who forgets everything between letters. If you reply "yes, here is the answer" without restating their question, they can't make sense of it. Every letter has to carry the whole thread.

The answer. The Messages API is stateless. It keeps nothing between calls. Your loop owns the history, and must send all of it, every time.

There are three formatting rules. Break any of them, and you get an API error. Not a weaker answer. An error.

First. You append the assistant message that contains the tool_use block. Each tool_use block carries an id.

Second. You follow it immediately with a user message holding one tool_result per tool_use id. Each result's tool_use_id field matches. Nothing goes in between.

Third. Inside that user message, the tool_result blocks come first, before any text.

A tool_result can also carry an optional is_error flag, for reporting a failed call.

So what happens if you remove the assistant message? The tool_result points at an id that no longer exists. The request is rejected.

Now the wrong turns.

Wrong: the API remembers the assistant turn on the server, and a stale session id needs refreshing. Why? The Messages API holds no server-side memory at all.

Wrong: the result lacks is_error set to false. Why? That flag is optional. Its absence can't cause a rejection.

Wrong: max_tokens is too low. Why? Output length has nothing to do with a malformed history.

And if you want to save tokens? Trim the tool output instead.

Hold on to this line. The API forgets everything. So every request carries the full history, and every tool result sits right after the request it answers.

Now the length limits.

In plain words, a response can be cut off for two different reasons. Either the answer itself ran out of room. Or the whole working space was already full.

To careless code, they look the same. Why? Because a cut-off answer arrives looking just like a finished one.

Think of a filing cabinet so full that nothing new fits. Buying a bigger envelope for the report doesn't help. The problem is the cabinet, not the envelope.

In exam terms, here are the two.

First. max_tokens means the output hit the max_tokens limit you set on the request. The response is truncated. The fix is to raise the limit, or continue the response.

Second. model_context_window_exceeded means the response filled the model's entire context window. That's also truncation. But raising max_tokens can't help. The window is full, no matter how large the output allowance is.

So what do you do instead? You compact the conversation. Summarise. Or move the work into subagents that each start with a fresh window.

In both cases, you never parse the truncated output as a finished artifact.

One small detail from the notes. model_context_window_exceeded is typed only in the software development kits' beta namespace. And on models older than Claude Sonnet four point five, it needs a beta header. Handle it either way.

Question three.

Here's the scenario. A contract extraction pipeline processes merger bundles of several hundred pages, in one conversation. On the largest bundles, the final response arrives with model_context_window_exceeded. And the partial JSON is stored as if complete.

The team proposes doubling max_tokens.

What's the right answer?

Take a second.

The answer. Mark the response truncated. Then compact the context, or move per-document extraction into fresh subagents.

Now the wrong turns.

Wrong: double max_tokens. Why? That's the remedy for a different stop reason.

Wrong: retry at a lower temperature. Why? It doesn't change how much context the bundle consumes. It's a global remedy, applied without a diagnosis.

And the nastiest trap. Wrong: a JSON repair step that closes the unterminated brackets. Why? That produces valid JSON with missing clauses. It looks complete downstream. And that is worse than a visible failure.

The notes add a close cousin.

A nightly batch. On about two percent of nights, the parser fails on malformed JSON. And on a few nights, it stores an invoice with three of its eleven line items missing.

Both symptoms are the same thing. Truncation, passed downstream as if finished.

And they won't reproduce interactively. Why not? Because short test documents never hit the limits.

Hold on to this line. max_tokens means the envelope was too small. model_context_window_exceeded means the cabinet is full. Neither is a finished answer.

Next, pause_turn.

In plain words, sometimes the model is doing a lot of work inside a single turn, and hits an internal step limit. It stops. It effectively leaves a note saying it paused here, and someone should pick it up. It has not finished.

Picture a courier who reaches the end of a shift halfway through a route. They leave a note: "route paused at stop ten." If the dispatcher files that note as delivered, half the parcels never arrive.

The technical name is the pause_turn stop reason. It appears when a server-side tool loop, such as the built-in web search, reaches its iteration limit. That limit defaults to ten.

It's a continuation point, not a completion. You append the assistant content to the history, and send another request. The same turn resumes, without redoing earlier work.

Question four.

Here's the scenario. A research assistant uses server-side web search. The loop continues only on tool_use, and returns the text for anything else. On broad questions, answers stop mid-thought, with no error. The logs show pause_turn.

Which fix costs least?

Take a second.

The answer. Append the assistant content, and send another request.

Now the wrong turns.

Wrong: raise max_tokens. Why? Output truncation reports max_tokens, not pause_turn.

Wrong: treat it like a refusal, and retry on a fallback model. Why? That throws away progress and doubles cost.

Wrong: raise the loop's own turn cap. Why? That cap never fired. The loop exited because it misread pause_turn as completion.

refusal is the opposite case. It's terminal for that path.

A companion field called stop_details is filled in only on a refusal. It names the policy category that triggered it. For every other stop reason, it's null.

The correct action? Read stop_details. Then either retry on a fallback model, or escalate. You never loop on a refusal.

So when do you use which? Here's the contrast, one at a time.

tool_use: run the tools, and continue.

end_turn: exit, then check the work yourself.

max_tokens: truncated. So raise the limit, or continue.

model_context_window_exceeded: truncated. So shrink what one context holds.

pause_turn: not finished. So send it back.

refusal: stop this path. Read stop_details. Fall back, or escalate.

stop_sequence: read which one fired.

Hold on to this line. pause_turn means still going, send it back. refusal means stop here and escalate.

A quick word on the study material itself, because the sources disagree here.

The lesson one slide deck says end_turn is the only valid exit from a loop.

The written notes go further. They treat max_tokens and model_context_window_exceeded as truncation exits. They treat pause_turn as a continuation. And they add a code-checked acceptance test on top of end_turn.

Do these really conflict? Not really. The deck describes the normal, happy exit. The notes describe everything a production loop must handle.

So on the exam. If a question asks for the normal completion signal, the answer is end_turn. If it asks how a loop should handle truncation, a paused server tool, or a claim of success, use the fuller picture from the notes.

Now the heart of this part. Termination.

In plain words, a loop can fail in four different ways.

One. It can run too long.

Two. It can run too expensive.

Three. It can run stuck. Busy, but going nowhere.

Four. It can run wrong. Stopping, and claiming success, when the work was never done.

No single counter catches all four.

Picture a new hire. They say "done" at the end of every shift. And they keep phoning the same supplier, who never answers.

A good manager needs two checks. First, look for the signed delivery note before accepting "done". Second, step in when the same call has been made three times with nothing new.

Asking the hire to try harder? That fixes neither.

The technical version. You need four independent termination guards.

One. A turn cap. It bounds the worst case in round trips.

Two. A budget cap. It bounds it in money. Why do you need both? Because a single turn that reads a huge file can cost more than twenty cheap turns. So a turn cap does not bound spend.

Three. No-progress detection. It catches the loop that is busy and stuck. The usual technique is to record a signature for each tool call, meaning the tool name plus its arguments. Then halt after a bounded run of consecutive turns with no new signature. The notes use a limit of three.

Four. An acceptance check. It's run by your code, rather than claimed by the model. It decides whether an end_turn is actually a success.

The loop then returns a status the caller must inspect. Such as complete, halted, truncated, or refused.

Question five. This one is pick two.

Here's the scenario. A refund agent has a turn cap of thirty, and exits on end_turn. Some cases are logged as resolved, with no refund issued and no ticket. And some runs call lookup_order with identical arguments until the cap fires.

Leadership wants both failure classes caught, without raising cost.

Which two?

Take a second.

The answers. First. Have code verify that a refund id or escalation ticket exists before any case is logged as resolved. Second. Hash each tool name plus its arguments, and halt after a bounded run of turns with no new call signature.

Each guard catches a failure the other cannot.

Now the wrong turns.

Wrong: a system prompt sentence telling the agent not to finish until the issue is fully resolved. Why? That's advisory. The model can still end its turn on an unresolved case.

Wrong: raise the cap to sixty. Why? It makes the stuck runs more expensive. And it still doesn't notice nothing is happening.

Wrong: scan the final reply for the word "resolved". Why? Parsing the model's own words to decide completion is a named anti-pattern. Wording varies. And the word can appear without evidence.

Question six. A related one from the notes.

Here's the scenario. An incident agent calls log_search with the identical query fifteen or twenty times. Each time, it gets the same empty result. It only stops when an hourly token allowance cuts it off. The loop already has a turn cap of two hundred.

What's the fix?

Take a second.

The answer. No-progress detection.

Now the wrong turns.

Wrong: lower the cap to forty. Why? That just makes the failure cheaper, without detecting it.

Wrong: mark the empty result with is_error. Why? It's plausible, and harmful. An empty result is a valid answer. Calling it an error invites more retries.

Wrong: set tool_choice to auto. Why? It does nothing. auto is already the permissive default.

The words in a stem that point you here. "Identical calls, repeatedly" points to no-progress detection. "Resolved without evidence" points to an acceptance check.

Question seven. One more on termination, and this one is about the cap itself.

Here's the scenario. A pull request review agent in continuous integration runs a loop while its iteration counter is below six. When the counter hits six, it posts whatever it has as the finished review.

Small pull requests finish in three iterations. Large ones get cut off. And their partial reviews are posted as complete.

What's the right design?

Take a second.

A kitchen timer stops a pot boiling dry. But a cook who serves every dish the moment the timer rings will serve raw roasts and burnt toast. The timer is the backstop. The cook still checks whether the food is done.

The answer. In exam terms, an iteration cap is a circuit breaker, not a termination condition. The right design makes stop_reason the primary exit, and keeps the counter as a safety valve. When the counter fires, the run is reported as halted. Never as complete.

Now the wrong turns.

Wrong: raise the counter to thirty. Why? It's still the primary stop. And it still posts partial reviews as complete whenever it fires.

Wrong: remove the counter, and rely only on end_turn. Why? That deletes the safety valve, and leaves runaway runs unbounded. You demote the cap. You do not delete it.

Wrong: end each review with the phrase "REVIEW COMPLETE", and exit when it appears. Why? That's parsing words again.

Hold on to this line. The model stopping is a candidate. Your code decides success. And the cap only bounds the worst case, and reports halted.

Now the Agent SDK. That's the software development kit for building agents. It gives you the same guards as options, rather than hand-written code.

First, there's max_turns in Python, spelled maxTurns in TypeScript. One detail the exam likes. It counts tool-use turns only. The final text-only response is free.

Second, there's max_budget_usd, spelled maxBudgetUsd in TypeScript. It caps spend in dollars.

When either fires, the final ResultMessage carries a subtype other than success.

The subtypes are these five. success. error_max_turns. error_max_budget_usd. error_during_execution. And error_max_structured_output_retries.

The result text field exists only on success. So you check the subtype before you read the result. That's mandatory. Not defensive.

Question eight. The notes have one on this.

Here's the scenario. A wrapper reads the result field and writes it to a report file. On long tasks, the file is sometimes created empty. The process exits with a nonzero code. And the alert just says "unexpected error."

Which two fixes?

Take a second.

The answer. First. Check the subtype before reading the result. Second. Wrap the iteration in a try block. Why? Because a single-shot query yields the final error result, and then raises.

Now the wrong turns.

Wrong: set maxTurns very high. Why? That removes the guard.

Wrong: read stop_reason instead of the subtype. Why? The subtype tells you why the loop ended. stop_reason tells you why the model stopped on its final turn. And it's null on a result synthesised after a crash.

Finally, on the Messages API side. There's a beta helper called the Tool Runner that wraps the loop for you. It takes a max_iterations parameter. And it exits when the model stops calling tools, or when that limit is reached.

That's part one.

If you remember one thing, make it this. Read stop_reason on every response. Treat truncation as truncation. Send pause_turn back. And let four guards, not the model, decide when the run is over.

Part two: Coordinators and subagents

Part two. Coordinators and subagents.

This is task statement one point two: orchestrate multi-agent systems with coordinator-subagent patterns. By the end of this part, you'll know how to pick between one agent, a coordinator, and plain code. Why everything routes through the hub. When to fan out. And how to bound the whole tree.

Let's start with a picture.

You send three people into a supermarket, each with a third of the list. You stand at the entrance. You hold the list. You decide who takes what. And you check the trolley at the end. They walk the aisles.

What do you gain? You never hear about the aisles. Three people walked for an hour, and you got three short reports.

What do you pay? None of them can see the others' baskets. And you pay for all three trips, whether or not you use what they bring.

That's a coordinator.

And there's a third option people skip. If you know exactly what's on the list, in what order, and it's the same every week, you don't need anyone exercising judgment at all. You need a checklist, and someone following it.

The technical names are these. Three shapes.

One. A single agent, running one loop.

Two. A coordinator with subagents.

Three. A deterministic pipeline. That means plain code that runs fixed steps in a fixed order.

When does each one fit, and how does each one fail?

A single agent suits one thread of reasoning, where each step depends on the last. It fails by filling its context window, and losing early instructions.

A coordinator with subagents suits independent subtasks that each produce a lot of verbose intermediate work. Each subagent keeps that work in its own window. Only its final message returns. It fails through fan-out cost, duplicated work, and context lost at the boundary.

A deterministic pipeline suits work whose steps and order are known in advance. It's predictable. It's easy to cost. And it fails only by meeting something its author did not anticipate.

The deciding test is one question. Does the next step depend on the content of the previous result?

Compile, then test, then deploy. That's a pipeline.

Read a failure, form a hypothesis, choose where to look next. That's an agent.

And very often, the best answer is a narrow agent inside one stage of a pipeline.

Question one.

Here's the scenario. An on-call assistant reads an arbitrary production alert. It picks each next diagnostic, out of about forty, based on what the last one returned.

A platform lead wants to replace it with a fixed pipeline that runs a standard set, in a standard order. The surrounding steps never vary: opening a ticket, attaching output, and paging the owner.

What's the right design?

Take a second.

Think of a hospital. It doesn't let doctors improvise the admission paperwork. And it doesn't force them to follow a fixed script when diagnosing. The forms follow a checklist. The diagnosis follows the clues.

The answer. Make the fixed steps a deterministic pipeline. Keep a bounded agent loop only for the diagnosis stage.

Now the wrong turns.

Wrong: replace everything with the fixed pipeline. Why? A fixed order can't follow an alert where each result decides the next step. So it runs irrelevant checks, and misses the right one.

Wrong: run all forty diagnostics as parallel subagents. Why? That pays for every branch, whether needed or not. And it ignores the dependency between steps.

Wrong: keep one agent for the whole workflow, with a higher turn cap. Why? That pays latency and unpredictability to rediscover a flowchart you already own. And it risks a skipped page.

Question two. The notes run the same idea the other way round.

Here's the scenario. A release-notes generator fetches a diff, classifies the change, renders a paragraph, and appends it. Always in that order. A colleague proposes a coordinator with four specialist subagents.

What's the answer?

Take a second.

The answer. A deterministic pipeline in code, with a single narrow model call for classification. Why? Because classification is the only step that needs judgment.

Hold on to this line. If you can draw the flowchart before the run, write code. Use an agent only where the next step depends on what you just learned.

Next, the rule that workers don't talk to each other.

In plain words, everything goes through the coordinator. That's slower on paper, and safer in practice.

Pilots talk to the control tower, not to each other. Two pilots chatting directly might be quicker. But then nobody holds the full picture. And there's no record of who was told what.

The technical name is the hub-and-spoke pattern. Subagents never communicate directly. All routing passes through the coordinator.

That gives you two things. First, observability, meaning one complete record of every handoff. Second, central error handling, meaning one place where failures are detected and routed.

The coordinator owns the plan, the budget, and the acceptance criteria. The subagents own the work.

Question three.

Here's the scenario. A research coordinator routes each search subagent's findings to a report writer. An engineer proposes letting the search subagents send findings straight to the writer, to save latency.

Compliance requires a complete record of what each worker received and produced. And one place where failures are handled.

What do you do?

Take a second.

The answer. Keep all communication routed through the coordinator.

Now the wrong turns.

Wrong: approve direct routing, and have each subagent log its own messages. Why? That rebuilds the record after the fact. And it removes the single point where failures are caught.

Wrong: allow direct routing only for high-confidence findings. Why? A partial bypass still breaks the record, for exactly the traffic that skips the hub.

Wrong: merge search and writing into one subagent. Why? That floods the writer's window with verbose search output. And it still doesn't meet the audit requirement.

The constraint words are "complete record" and "one place where failures are handled." Those make the hub non-negotiable.

Now a failure that looks like a quality problem, and is really a structure problem.

Question four.

Here's the scenario. A market research coordinator spawns four parallel subagents. One. Analyst reports. Two. Regulatory filings. Three. Earnings call transcripts. Four. Social sentiment.

Each returns a solid, well-cited summary. Runs are fast. But clients complain the final report never connects a regulatory change to the sentiment shift that followed.

What's missing?

Take a second.

Four reporters each cover one beat for a newspaper, and every story is excellent. But no editor reads all four. So nobody notices that the council vote in one story explains the protest in another. The fix is an editor, not bigger notebooks.

The answer. In exam terms, the four lanes really are independent, so the parallel fan-out is correct. What's missing is a stage responsible for cross-source synthesis.

Siloed output from a multi-agent system usually signals a missing aggregation step. Not a model problem. Not a context problem.

So you add an explicit synthesis step. Such as a cross-source subagent whose job is finding intersections.

Now the wrong turns.

Wrong: a bigger context window for each subagent. Why? Nothing in the design asks anyone to connect the lanes, however much they can hold.

Wrong: let the four subagents exchange findings directly. Why? That breaks hub and spoke.

Wrong: give every subagent all four source tools. Why? That undoes the decomposition. It roughly quadruples cost. And it still leaves nobody owning synthesis.

Hold on to this line. Siloed results mean nobody was given the job of joining them up.

Next, speed.

In plain words, if three jobs don't need each other's answers, start them all at once. The total wait becomes the slowest job, not the sum of all three.

You need quotes from three builders. Calling the first, waiting a week, then calling the second, triples the wait for nothing. No quote depends on another. So you ask all three on the same day.

The technical version. Each delegation is a tool call.

A coordinator that issues one delegation call per turn, waits, then issues the next, runs its subagents in sequence.

A coordinator that emits several delegation calls in a single response runs them in parallel. Latency then equals the slowest branch.

Question five.

Here's the scenario. A code modernisation coordinator analyses three independent modules, about four minutes each. The phase takes twelve minutes. The transcripts show one call, a wait, then the next.

What's the fix?

Take a second.

The answer. Emit all three subagent calls in a single response.

Now the wrong turns.

Wrong: switch to a smaller model. Why? It may trim each branch, but it keeps the serial structure.

Wrong: raise the concurrent-subagent limit. Why? The documented default is twenty. That's far more than three. So that isn't what serialises them.

Wrong: merge the three into one subagent. Why? It's still sequential. And it pulls all three modules into one window.

The signature to recognise: latency roughly three times what it should be.

Now the contrast, because the exam tests it from both sides.

The deciding test for parallel versus sequential is this. Does any branch need another branch's findings? Findings. Not files.

Three auditors reading three different service directories are independent.

An auditor and a remediation planner are sequential. Even if they open no common file. Why? Because the planner's input is the auditor's output.

Question six. The notes include one on exactly this.

Here's the scenario. A coordinator spawns three vendor research subagents. And at the same time, a fourth that writes the recommendation. The recommendation keeps citing things the summaries contradict.

What's the fix?

Take a second.

The answer. Run the recommender after the other three.

Parallel fan-out over dependent stages gives you full cost, plus branches that contradict each other.

There's a failure-handling difference too. A sequential chain stops, and reports the stage that failed. A parallel fan-out collects each branch's outcome. So one failed branch doesn't void the others.

Hold on to this line. Parallel when no branch needs another's findings. Sequential when it does. And the test runs through conclusions, not the filesystem.

Question seven. One more coordinator failure from the notes.

Here's the scenario. A team adds subagents to a data quality agent, expecting token use to fall. Instead, it rises by about eighty percent. And the main conversation still fills up, even though the subagents return concise summaries.

What's the cause?

Take a second.

The answer. The coordinator is re-reading the same tables, and rerunning the same queries, after its workers report. It pays for the work twice.

The fix is to constrain the coordinator's own tools. And instruct it to gather, combine and route. Not to investigate.

Now the wrong turn.

Wrong: each subagent inherits the parent's full history. It's tempting. Why is it wrong? Because it doesn't. A subagent starts fresh.

Now bounding the tree.

In plain words, anything that can delegate can delegate to something that delegates. Left alone, one request can grow into a tree of agents. And the bill grows with it.

So you need two things. One limit on money that covers everyone. And one rule on how many layers of delegation are allowed.

Picture a project manager. They give the team one company card, whose limit covers everyone. And they rule that contractors may not hire subcontractors.

Limiting how many phone calls each contractor makes wouldn't stop one expensive purchase. And a polite request not to subcontract is easy to ignore.

The technical version has four settings. I'll take them one at a time.

First. The coordinator delegates through a built-in tool called Agent. That tool must be listed in the coordinator's allowedTools. If it isn't, every delegation falls through to a permission decision. And in modes that never prompt, it's denied.

The symptom? Claude doing all the work itself, with no Agent calls anywhere in the transcript.

Second. maxBudgetUsd covers the whole tree. Why? Because subagent requests count toward the query's total_cost_usd. At the cap, the query refuses new subagents.

Third. The environment variable CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH caps nesting. It defaults to three layers below the main agent. Setting it to one lets the main agent delegate, while its workers cannot.

Fourth. CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS caps how many run at once. It defaults to twenty. Beyond that, a spawn fails with the message "Concurrent subagent limit reached."

And the notes add one thing. Opus-class models delegate more readily than earlier ones. So these bounds matter more than they used to.

Question eight. This one is pick two.

Part four. Enforcement and handoffs.

This is task statement one point four: implement multi-step workflows with enforcement and handoff patterns. By the end of this part, you'll know the three rungs of the enforcement ladder, what a handoff record must carry, and how a handoff to a human differs from one between stages.

Let's start with a picture.

A sign in a staff kitchen asking people to wash up is a request. A barrier that won't open until you tap a card is a guarantee.

Both express the same wish. Only one of them holds on the day somebody is in a hurry.

Instructions in a prompt are the sign. Most of the time they work. And that's exactly the trap.

A rule that holds nineteen times out of twenty looks like a rule. Right up until the twentieth run writes to something that matters.

If a step must happen, something outside the model's judgment has to check that it happened. Every time.

The technical principle. Hold on to this line. A prompt is a request, and code is a guarantee.

If a step must happen, encode it as a gate your code evaluates. Not as a sentence competing with everything else in the context window.

And there's an order in which you reach for enforcement. It's called the enforcement ladder. Three rungs.

First. Structural. Withhold the tool. A stage that must not write has no write tool in its tools list.

Second. Deterministic interception. A PreToolUse hook that denies the call outright. No amount of model reasoning can route around it.

Third. Contractual. A handoff record the next stage validates before it does anything. So an out-of-order or incomplete stage fails loudly, at the boundary.

The price is the same in all three. You give up some flexibility. And every gate is code someone has to maintain.

Question one. A prerequisite gate.

Here's the scenario. An account-security agent can call verify_identity and reset_password. Despite clear system prompt instructions, audit logs show about one reset in two hundred happening before identity was verified.

Compliance requires zero exceptions. And when a reset is blocked, the agent should explain why and escalate, rather than retry.

What's the answer?

Take a second.

A bank teller's cash drawer stays locked until the ID scanner turns green. The teller can't hand over money first and check ID later, however long the queue. If the scanner refuses, a message tells the teller to call a supervisor.

The answer. A PreToolUse hook that tracks session state, and denies reset_password until verify_identity has succeeded.

It runs in code, before the call executes. So the model can't bypass it.

And the denial carries a permissionDecisionReason. For example: "Identity not verified. Do not retry. Escalate." That reason gives the model the context to escalate, instead of retrying with different parameters.

Now the wrong turns.

Wrong: a PostToolUse hook that flags unverified resets for review. Why? PostToolUse runs after the tool has already executed. So the reset has already happened. It detects. It does not prevent.

Wrong: move the rule into CLAUDE.md. Why? That helps a rule persist. But it's still advisory. And most of the time is not zero exceptions.

Wrong: add few-shot examples showing verification first. Why? Examples improve consistency, not compliance.

The constraint words that decide it are "zero exceptions" and "explain and escalate rather than retry."

Hold on to this line. If one step must come before another every time, block the second step in code until the first has succeeded. And say why.

Part five: Hooks for interception and normalization

Part five. Hooks.

This is task statement one point five: apply Agent SDK hooks for tool call interception and data normalization. By the end of this part, you'll know the main hook events, how a PreToolUse hook answers, how to clean results on the way back, why async hooks can't change anything, and who wins when hooks disagree.

Let's start with a picture.

Think of the counter at a post office. You bring a parcel. The clerk weighs it. Rewrites the address into the format the sorting machines want. Tells you the customs form is missing. Or refuses the parcel outright.

You never had to know any of those rules. And no amount of insisting changes what the clerk does. Why? Because the rules live at the counter, not in your head.

Hooks are that counter. They're placed between the agent and everything it tries to do.

They're code you write that runs at fixed moments. Before a call goes out. After a result comes back. When a worker starts. When a run ends.

Because they run inside your program, rather than inside the conversation, they take none of the model's attention. And they can't be argued with.

Two uses follow.

One. You can stop something happening.

Two. You can correct the shape of something, on the way out, or on the way back.

A lot of what looks like a model getting a format wrong is really a mismatch nobody put a translator in front of.

The technical version. Hooks are the one place in an agentic system where you get deterministic control over a nondeterministic actor.

They run in your application process, not in the context window. So they cost no tokens. And they can't be talked out of a decision.

The events have real names, and the exam expects you to know the main ones.

Available in both the Python and TypeScript SDKs are these. PreToolUse. PostToolUse. PostToolUseFailure. UserPromptSubmit. Stop. SubagentStart. SubagentStop. PreCompact. PermissionRequest. And Notification.

TypeScript has a longer list on top, including SessionStart and SessionEnd. Though those are also reachable from Python, as shell command hooks declared in a settings file.

The notes warn that this list has roughly doubled in a year. So treat it as a snapshot. And never assume an unfamiliar event name is invented.

For this domain, six matter most.

One. PreToolUse, for intercepting a call and rewriting its arguments.

Two. PostToolUse, for normalising results, and auditing.

Three and four. SubagentStart and SubagentStop, for tracking and aggregating delegated work.

Five. Stop, for persisting state at the end of a run.

And six. PreCompact, for archiving a transcript before it's summarised away.

Stop has two documented jobs. First, it can save state before exit. Second, it's also a blocking event. A Stop hook that rejects prevents Claude from stopping, and continues the conversation. That second job is the verification gate the configuration chapter builds on.

Now the return shape of a PreToolUse hook.

Every callback receives three things. The event input. A tool use id, which links a PreToolUse to the PostToolUse for the same call. And a context object.

All hook inputs share session_id, cwd, and hook_event_name. And agent_id and agent_type are filled in when the hook fires inside a subagent.

The return has top-level fields, such as systemMessage and continue. continue is spelled continue_ in Python. And it has a hookSpecificOutput section.

For PreToolUse, hookSpecificOutput carries a permissionDecision. That's one of four values: allow, deny, ask, or defer. Plus a permissionDecisionReason, and an updatedInput.

The pairing rules matter. One at a time.

Pair updatedInput with allow, to auto-approve the rewritten call.

Pair it with ask, to show the rewrite to the user.

Leave permissionDecision out, and the modified input still applies, under normal permission evaluation.

And defer ignores updatedInput entirely.

You return a new object, rather than changing tool_input in place. And you return an empty object to allow the call unchanged.

Hooks are registered with a matcher, tested against the tool name. A hook with no matcher fires for every call of its event type.

Part six. Decomposing complex work.

Let's start with a picture.

The technical version. Hold on to this line. Decomposition buys isolation, and costs context.

What do you gain? A fresh window. A narrower set of tools. A cheaper model, where the work is cheap. And a piece that can fail without taking the others down.

What do you pay? You rebuild, in a prompt, everything the child would otherwise have known. Plus a return trip through the parent.

The notes put the rule as three signals to split on. Context volume. Permission asymmetry. And verification independence.

One. Split when a subtask throws off logs or search hits that nobody needs afterwards.

Two. Split when one part needs write access, and the rest should be read-only.

Three. Split when each piece has its own pass or fail check.

And when do you keep work whole?

First. When every intermediate result feeds the next decision.

Second. When success can only be judged across the whole result.

Third. When piece two needs piece one's conclusions.

Fourth. When the work is refine and recheck.

Fifth. When latency matters, and a fresh subagent's cold start would dominate.

In plain words, some work is a checklist. And some work is a detective story.

Prompt chaining is a fixed sequence of prompts, where each step's output feeds the next. It's reproducible, and auditable.

Dynamic decomposition lets the agent work out the subtasks as it goes, based on what it finds. It suits investigations, and open-ended work.

Part seven. Sessions, resumption and forking.

This is task statement one point seven: manage session state, resumption, and forking. By the end of this part, you'll know when to resume, when to fork, when to start fresh, and how to recover from a crash without leaning on a transcript.

Let's start with a picture.

Come back to a half-finished job after a week away. Your notes are both the reason you can pick it up, and the reason you can get it badly wrong.

The notes record exactly what you believed when you put them down. They say nothing about the fact that somebody tidied the room. Or that the ladder you left against the wall has been borrowed.

You act on the notes with total confidence. Because from your point of view, no time has passed.

A saved session is that notebook. It holds the conversation. What was said. What was found. What was decided. It holds nothing about the world those statements were about.

And there's a second move worth knowing.

Before trying an alternative approach, you can scribble the new plan over the page you have. Or you can photocopy the page, and scribble on the copy. The copy costs almost nothing, and keeps the original safe.

But here the analogy has a sharp edge. Photocopying the notebook gives you two notebooks. And there's still only one room. Two plans acting on the same room still collide.

The technical version.

The SDK writes each session to disk as you work. As JSONL files under ~/.claude/projects/, in a folder named after the encoded working directory.

There are three ways back in. One at a time.

One. continue. It's spelled continue: true in TypeScript, and continue_conversation=True in Python. It picks up the most recent session in the current directory, with no id to track.

Two. resume. It takes a specific session id, captured from session_id on the result message. It's what you need when several conversations run at once.

Three. fork_session in Python, or forkSession in TypeScript, used together with resume. It creates a new session that starts with a copy of the original's history, and diverges from there.

In Claude Code, the same three appear as claude --continue, claude --resume, and --fork-session, or the /branch command.

The distinction the exam probes.

continue and resume both add to an existing session. So its history grows.

Fork copies the history into a new session id. And it leaves the original untouched.

And the caveat the exam loves most.

The documentation says sessions persist the conversation, not the filesystem. And forking branches the conversation history, not the filesystem.

So if a forked agent edits files, those changes are real. And they're visible to any session working in the same directory.

Hold on to this line. Resumption restores what the agent knew, not what is now true.

Trap round

The trap round.

Time for rapid fire. I say what you might see in a question. You think of the answer. We'll go in the order of the parts.

First, loops.

If you see a loop that exits when the first content block is text, think: it should branch on stop_reason. Text and a tool request can arrive together.

If you see an API error right after someone stopped sending the assistant message, think: the API is stateless. Every tool_result must follow its tool_use.

If you see partial JSON stored as complete, think: truncation. max_tokens means raise the limit, or continue. model_context_window_exceeded means shrink the context, or move work into fresh subagents.

If you see a server tool, and an answer that stops mid-thought, think: pause_turn. Send the content back.

If you see a refusal, think: terminal. Read stop_details. Fall back, or escalate. Never loop.

Still on loops.

If you see the same tool called with the same arguments, over and over, think: no-progress detection. Not a higher turn cap.

If you see "resolved" with no evidence, think: an acceptance check in code. Not a prompt sentence. And not a keyword scan.

If you see a turn cap used as the finish line, think: stop_reason is the primary exit. The cap is a safety valve that reports halted.

If you see an empty result file from an SDK wrapper, think: check the ResultMessage subtype before reading result.

Now coordinators and subagents.

If you see fixed steps in a fixed order handed to an agent, think: deterministic pipeline. With an agent only where judgment is needed.

If you see subagents talking directly to each other, think: hub and spoke. Everything through the coordinator.

If you see excellent separate summaries that never connect, think: a missing synthesis step.

If you see latency about three times what it should be, think: emit all the independent subagent calls in one response.

If you see a recommender running in parallel with the researchers it depends on, think: dependency on findings means sequential.

Still on coordinators.

If you see token use rising after adding subagents, think: the coordinator is redoing its workers' work.

If you see a delegation tree growing deep and expensive, think: maxBudgetUsd for the whole tree, and spawn depth one. Or remove Agent from the one subagent that must not delegate.

If you see Claude never delegating at all, think: Agent is missing from allowedTools.

If you see a capped run labelled complete, think: error_max_budget_usd is incomplete. Report the coverage gap.

Now spawning and context.

If you see a subagent that can't find a file the parent just read, think: the delegation prompt was not a self-contained work order.

If you see a rule in the coordinator's system prompt that subagents ignore, think: the parent's system prompt never crosses. Use CLAUDE.md, or the subagent's own prompt.

If you see identical subagent descriptions and misrouting, think: rewrite each description as a routing rule. Not a coordinator prompt patch.

If you see a subagent that must never call a tool, think: leave it out of that subagent's tools list. Not allowed-tools in a skill. Not readOnlyHint. Not a prompt line.

If you see prose summaries and untraceable claims, think: structured findings, with source metadata and claim-to-source ids.

If you see two sources that disagree, think: record both. Mark unresolved. Escalate.

Now enforcement and handoffs.

If you see a step that must happen before another every time, think: a PreToolUse gate, with a permissionDecisionReason. Not PostToolUse, which is too late.

If you see a rule forgotten after compaction, think: CLAUDE.md for persistence. A hook for enforcement.

If you see a stage acting on a stale handoff, think: validate run_id, next_expected, a code-evaluated gate, and the checksum. Then refuse on mismatch.

If you see "validation passed" in prose, think: a claim, not evidence. evaluated_by code.

If you see units drifting between stages, think: decisions_locked.

If you see humans reading transcripts to act on escalations, think: a structured handoff summary.

Now hooks.

If you see raw codes and epoch timestamps being misread, think: normalise in PostToolUse.

If you see a huge tool result filling the window, think: updatedToolOutput, with a path back to the raw output.

If you see worry about hook order, think: deny beats defer beats ask beats allow. Order does not matter.

If you see an async hook that was supposed to rewrite or block, think: it can't. Async is for logging only.

Now decomposition.

If you see a fixed audited checklist versus an unknown investigation, think: prompt chaining versus dynamic decomposition.

If you see subagents split by directory missing cross-boundary flows, think: decompose by question, not territory.

If you see a writer and reviewer subagent ping-ponging with rising cost, think: keep refinement in one conversation.

And finally, sessions.

If you see a resumed session with a few known file changes, think: resume, and state what changed.

If you see two alternatives from one expensive baseline, think: fork. And give each fork its own working copy.

If you see a resumed session citing files that no longer exist, think: fresh start, with findings framed as hypotheses.

If you see a job that restarts from zero when the container recycles, think: a structured state record. Not transcript shipping.

That's the trap round.

Closing recap: ten things to remember

The closing recap. Ten things to remember from this chapter.

For each one, you'll hear the idea in plain words first. Then the technical name that goes with it.

One. The model stopping is not the job being done. Read why it stopped, every time. And let your own code judge success.

The technical name is branching on stop_reason. With end_turn as a candidate, and a code-evaluated acceptance check.

Two. A loop fails by running long, expensive, stuck, or wrong. So it needs four separate guards. And the counter is only the backstop.

The technical name is the four termination guards. Turn cap. Budget cap. No-progress detection. And an acceptance check. With the cap reporting halted.

Three. A cut-off answer looks like a finished one. And a paused answer is not finished at all.

The technical names are max_tokens and model_context_window_exceeded as truncation. And pause_turn as a continuation.

Four. If you can draw the flowchart before the run, write code. Use an agent only where the next step depends on what was just found.

The technical name is choosing between a deterministic pipeline, a single agent, and a coordinator with subagents.

Five. Workers report to the coordinator, never to each other. Independent work runs at the same time. Dependent work waits its turn.

The technical names are hub and spoke. And parallel spawning, by emitting several Agent calls in one response, decided by the dependency test on findings.

Six. Cap the whole tree's spending and depth. And never call a capped run complete.

The technical names are maxBudgetUsd. CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH set to one. And treating error_max_budget_usd as incomplete, with coverage reported.

Seven. A worker knows only what you write down for it. And a worker should simply not be given tools it must never use.

The technical names are the self-contained delegation prompt. The description as a routing rule. And the tools availability list, which restricts. Unlike allowedTools, skill allowed-tools, or readOnlyHint.

Eight. A prompt is a request, and code is a guarantee. So enforce in order. Take the tool away. Block the call. Then check the paperwork at the next stage.

The technical name is the enforcement ladder. Withheld tools. A PreToolUse deny with a reason. And a validated handoff record with decisions_locked. With CLAUDE.md for persistence across compaction.

Nine. Hooks are code at the counter. One guards what goes out. One cleans what comes back. A veto always wins. And anything meant to change the outcome must not run in the background.

The technical names are PreToolUse. PostToolUse with updatedToolOutput. The precedence deny, defer, ask, allow. And no async for normalisation.

Ten. A saved session remembers the conversation, not the world. Resume when little has changed, and say what did. Fork to explore, on separate copies of the files. Start fresh with hypotheses when a lot has changed. And survive crashes with a small written record.

The technical names are resume. fork_session. A fresh session with injected state. And a structured state record, written atomically.
